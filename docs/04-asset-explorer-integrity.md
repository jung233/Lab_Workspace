# 04｜原始文件 Explorer、存储回收与分级 SHA-256 完整性策略

## 4.1 本章与旧版的主要变化

**新增 File Explorer 为一级主导航入口**。用户可以直接查找、浏览、系统打开、批量导出和删除原始文件及派生文件；文件删除不是在操作系统里直接 `rm`，必须有链接影响分析、回收站、同步墓碑和空间回收逻辑。

**SHA-256 不再对全部大型文件的每次打开强制全文重算**。将导入计算、日常快速检查、按需深度完整性验证明确拆分。

## 4.2 原件存储与文件路径

真实字节按 SHA-256 内容寻址：`store/objects/sha256/ab/cd/<64hex>`。SQLite 中分离：

- `BlobObject`：`sha256`, `byte_size`, `storage_path`, `state`, `import_verified_at`, `last_full_verify_at`, `last_fast_check_at`, `last_fs_size`, `last_fs_mtime_ns`, `last_file_id`, `integrity_policy_snapshot`。
- `Asset`：`asset_id`, `blob_sha256`, `name`, `mime`, `kind=raw|derived|thumbnail|report`, `created_at`, `origin`, `parent_asset_id`。
- `AssetLink`：关联 ExperimentRun、StepExecution、Sample、Measurement、CalculationRun、AnalysisRun；物理 CAS 不存“实验文件夹”路径。
- `DeletionRecord`：Asset 脱钩/回收、用户确认、影响对象、时间、原因、删除目的及状态。
- `RemoteObjectReplica`：哪些云端目标有此对象及其是否已上传/校验。

单个 Blob 可以被多个 Asset 引用，一个 Asset 可以同时链接多个步骤。大文件去重避免重复存储，但不能误以为删除一个链接就是可以物理删除内容。

## 4.3 SHA-256 三阶段策略

用户设置：`settings.integrity.strict_size_threshold_bytes`，默认 `2 * 1024^3`（**2 GiB = 2,147,483,648 字节**，UI 可显示约 2.15 GB）；合法配置区间由产品约束（建议 128 MiB 到 64 GiB），可选择“全部严格验证”或“只导入与定期验证”。阈值调整应影响后续访问策略，不重写已经存储的原始哈希。

| 阶段 | 文件 <= 阈值 | 文件 > 阈值 | 说明 |
|---|---|---|---|
| 第一次导入 APP | **流式计算完整 SHA-256** | **流式计算完整 SHA-256** | 全部保存原件必须具有初始哈希，尽可能边复制边算，避免额外读取遍 |
| 导入完成后 | 依据哈希验证提交 | 依据哈希验证提交（可利用写入同一遍的哈希，不强制再读全文件） | 两阶段提交/断电恢复 |
| 每次逻辑文件打开读取 | **完整内容 SHA-256 校验**，不匹配阻断 | 仅尺寸、mtime、文件 ID 等快速检查（可配置） | “每次”指一个完整逻辑打开/读取操作，而非 read() 每个缓冲块重复哈希 |
| 编辑后写入新文件 | 计算新 SHA-256 并确保新 Asset | 同样计算一次新 SHA-256，不反复重扫 | 禁止覆盖已提交原件 |
| 复制/同步前 | 先严格复验源文件 | 默认快速检查，可选本次全量校验 | 大文件未经本次重算只能声明 `previously_verified`，不能说已确认最新字节正确 |
| 远端下载完成 | 复验 SHA-256（通常可在接收流式过程中计算） | 可在传输流中校验整份 SHA，不需额外读取一遍；若禁用则标记未全验 | 支持仅传输校验策略，明确置信状态 |
| 定时后台核验 | 用户设频率 | 用户独立设频率（默认“仅闲时/手动”） | 需电源/Wi-Fi/温度策略、可暂停 |
| 用户点击“校验此文件” | 强制全量 | 强制全量 | 不受阈值限制，显示进度/可取消 |
| 恢复备份 | 推荐强制全验 | 用户可选“快速恢复”后后台复验或“严格恢复”当场全验 | 没有全验不能显示为 cryptographically verified |

**大文件快速检查不是完整性证明**：尺寸/修改时间可能没变但内容已变化；应保留首次导入时记录的 SHA-256 和 `last_full_verify_at`，UI 标记 `快速检查通过 / 上次完整验证时间`，绝不将快速检查标为 SHA-256 校验通过。

若存储空间/时间允许，可可选生成分块 SHA-256 / Merkle Tree 辅助大文件定位损坏块、增量校验，但它不能消除首次完整读取成本。文件系统无法对整个原文件提供强保证时，不把“不重算 SHA”描述为“保证未被修改”。

### 4.3.1 完整性状态

- `verified`：本次或最近指定策略的完整 SHA-256 核对通过；附时间。
- `quick_checked`：文件属性一致，仅快速校验；保留上次 full verify 时间。
- `verification_overdue`：超过完整校验计划/用户配置。
- `mismatch`：完整哈希不匹配或快检发现明显变化；隔离禁止新科学计算。
- `missing`：文件缺失；可按已配置副本恢复。
- `pending`：新文件尚未获得可核实初始 SHA，不能标为可归档。

### 4.3.2 入库 IO 与原子性

1. `file_picker` 获得用户授权输入流；流式复制到 staging，并在同一次流过计算 SHA-256。
2. 调用 fsync/平台持久化 API；将预期 Blob（staged）与源信息写入 SQLite。
3. 在同一文件系统内原子发布到 CAS 路径；如果同路径已存在，核对存储对象基本信息，按政策全量/快速核查后复用。
4. SQLite 提交 Blob committed + Asset + AssetLink + MutationEvent。
5. 崩溃恢复扫描 staging、孤儿 CAS、staged 记录，完成或隔离；不允许把 staging 中间态暴露为正式原件。

事务跨 SQLite 和文件系统不是天然原子，必须引入补偿恢复协调器；不应为了省事直接将“用户原路径”作为唯一数据存储。

## 4.4 File Explorer 功能设计

### 4.4.1 页面布局

Windows 建议资源管理器式三栏：左边**虚拟目录树**，中间**文件表格/缩略图**，右边**元数据与引用详情**。移动端采用层级列表与底部操作菜单。

虚拟目录：

```text
Lab Workspace Files
├── 全部文件
├── 项目 / Project → 实验 → Step
├── 样本 / Sample
├── 原始文件 Raw
├── 衍生文件 Derived / AI 输出 / 计算结果
├── 已产生但未关联文件 Orphans
├── 最近导入/最近打开
├── 本机独有文件
├── 仅远端文件（按需下载）
├── 待校验/完整性警告
└── 回收站
```

支持文件名、样本/实验标签、格式、大小区间、导入日期、`large/small`、同步状态、原件/派生类型、占用空间与引用数量筛选。

### 4.4.2 每个文件的操作

- 打开/预览（支持操作系统默认查看器，避免 APP 强制实现所有科研文件解析）；
- Windows “在文件资源管理器中显示”；移动端用系统 Share Sheet / Open in；
- 导出原件为**可编辑副本**，明确说明修改不会改变 Vault 已归档原件；重新导入形成新 Asset；
- 复制/移动虚拟目录位置（不复制原始 Blob），编辑标签和显示名；
- 查看源文件、来源实验、文件原始 SHA、上次全验时间、同步/备份状态；
- 关联到其他实验、解除关联、复制下载链接（内部引用）；
- 计算或重新核验 SHA-256；
- 批量删除、移入回收站、立即永久删除（安全确认）；
- 点击“查看派生链”：原始→裁剪/标注→分析输出→报告。

### 4.4.3 必须区分三种删除

1. **移除某条引用**（Unlink）：把此文件从该实验/步骤移除；其他 AssetLink 不变，不回收 Blob。
2. **删除 Asset/移动到回收站**：将逻辑文件标记为 deleted，其他对相同 Blob 的 Asset 仍可用；30 天默认软删宽限期可配置。
3. **释放物理空间（Purge/GC）**：条件满足时删除 Blob 的最后物理副本。必须检查所有活动 Asset、回收站保留期限、未同步设备的墓碑、备份保留记录、运行中的计算/导出及文件句柄；删除前清楚列出“将删除的实际字节”。

即使原件仍被引用，用户也可进入“强制删除原始文件”的受控流程：首先显示受影响实验/结果/分析清单，要求明确确认，生成 tombstone 和已缺失标记，使历史实验保留引用与缺失提示，而不是因阻止用户删除造成无法优化空间。

### 4.4.4 空间清理视图

区分 `logical_bytes`（显示文件大小总和）、`unique_blob_bytes`（去重后真实占用）、`cache_bytes`、`trash_bytes`、`remote_only_bytes`、`backup_bytes`，不能把同一 Blob 多次算作可回收空间。清理候选按：无引用文件、可重建缩略图、过期临时文件、已同步且允许释放的本地大文件、回收站到期文件排列。用户逐条确认或按已设置策略执行，必须有恢复建议。

## 4.5 两种原始数据模式

**Managed Import（默认）**：完整复制原件到 Vault CAS；独立于用户原来的 Downloads、U盘、OneDrive 文件夹；系统能保证本地受管副本的生命周期。

**Linked External（可选）**：仅记外部文件位置和第一次扫描 SHA，不复制巨量原件；Explorer 中明确显示 `外部引用/本机可能不可恢复`，移动端可能没有永久授权；文件变动必须警告并建议重新导入成为新版本。外部引用不能自动声称跨端可同步，也不能作为唯一备份来源。

## 4.6 删除、安全恢复与远端行为

- 本地 soft delete 立即隐藏常规 Explorer，但可在回收站恢复；记录回收期限、操作者（单用户）、时间与影响列表。
- 云同步启用时同步 tombstone，其他设备收到后先把逻辑记录标记删除，但远端真实 Blob 可以等待设备确认与保留期再清理。
- 当备份仍引用 Blob 时，备份本身应保持其版本完整，不能因同步删除直接破坏独立备份。
- 物理删除后不能保证本地可找回，界面必须明确：已备份于哪个目标、上次成功校验、是否可恢复及密钥条件。未经验证的远端副本不能显示为“安全备份已存在”。
- 删除报告保留不可变的 Asset ID、最后已知 SHA、Blob 状态和必要的科学记录，允许查看“原始文件已删除”。
